## 0. 结论速览（拍板结果）

| # | 决策点 | 结论 |
|---|---|---|
| 1 | 题目管理员（problem_admin） | **只读**：可见自己被布置的作业、可浏览已发布作业，但不可建/改/删/下发 |
| 2 | 删除 | **软删除 + 仅创建者/root**；已有人提交时前端二次确认 |
| 3 | 「完成」定义 | **AC 制**：作业内所有题都被该学生 AC 即完成；`score` 字段保留给未来分数制 |
| 4 | 范围隔离 | **开启**：admin 只看/管自己创建的作业与学生组，root 全局 |
| 5 | navbar 闪烁范围 | **仅「必做且未完成」**闪烁 |
| 6 | 学生组模型 | **新建轻量 `student_group`**，不复用复杂的「团队」`group` 表 |
| 7 | 作业提交关联 | **`judge` 表加 `aid` 列** + `SubmitJudgeDTO` 加 `aid` 字段，走独立提交分支（仿 `cid`/`tid`/`pkId` 既有模式） |
| 8 | 完成判定挂载点 | **评测落库回调**：JudgeServer `JudgeContext.updateOtherTable()`，与 `user_acproblem`/`contest_record` 同处 |
| 9 | 时间窗 | 窗口内可提交、窗口外不可（仿比赛）；「进行中/已结束」由 `start_time`/`end_time` **动态推导，不落库翻转状态** |

## 1. 角色与权限（最终版）

角色对应（`sqlAndsetting/hoj.sql` 的 `role` 表）：`root`=1000、`admin`=1001、`problem_admin`=1008、其余为普通用户（学生）。

| 操作 | root | admin | problem_admin | 学生 |
|---|---|---|---|---|
| 新建/编辑/删除作业 | ✅ 全局 | ✅ 仅自己的 | ❌ | — |
| 发布/延期作业 | ✅ | ✅ 仅自己的 | ❌ | — |
| 学生组 CRUD | ✅ 全局 | ✅ 仅自己的 | ❌ | — |
| 查询（管理视图） | ✅ 全局 | ✅ 仅自己的 | 🔸 只读（全部已发布） | — |
| 查询（学生视图） | ✅ | ✅ | ✅ | ✅ 仅「布置给我的」 |

权限落地：
- 后端用 shiro 注解：读接口 `@RequiresRoles(value={"root","admin","problem_admin"}, logical=OR)`；写接口 `@RequiresRoles(value={"root","admin"}, logical=OR)`。
- 「仅自己的」：写/读时以 `creator_uid = 当前 uid` 过滤，`root` 跳过过滤。
- 前端用 `store/user.js` 的 `isAdminRole`（admin/problem_admin/root）控制管理入口可见性；`problem_admin` 额外隐藏「新建/编辑/删除/下发」按钮（后端仍强制兜底）。

## 2. 核心概念与「完成」定义

- **作业（Assignment）** = 一组题目 + 下发对象（学生）+ 时间窗口 + 是否必做。
- **必做（required）** = 截止前必须完成；未完成触发 navbar 闪烁。
- **「完成」= AC 制**：`assignment_student.accepted_count == 作业题目总数` 时置 `status=1(已完成)`，并写 `gmt_finish`。分数制（`score` 累计、阈值判完成）为后续可选项，字段已预留。

## 3. 数据模型（新增表 + 一列）

共 6 张新表 + `judge` 加 1 列。命名/类型/外键严格对齐现有 schema（uid → `user_info(uuid)` varchar(32)，题目 → `problem(id)`），迁移文件 `sqlAndsetting/hoj-assignment-update.sql` 用幂等写法（`CREATE TABLE IF NOT EXISTS` + `information_schema.COLUMNS` 守卫的 `ALTER TABLE`）。

### 3.1 `assignment` 作业

```sql
CREATE TABLE IF NOT EXISTS `assignment` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT COMMENT '作业ID',
  `title` varchar(200) NOT NULL COMMENT '作业标题',
  `description` mediumtext COMMENT '作业说明',
  `creator_uid` varchar(32) NOT NULL COMMENT '创建者uid(管理员)',
  `is_required` tinyint(1) NOT NULL DEFAULT '0' COMMENT '是否必做 1必做 0选做',
  `status` tinyint(4) NOT NULL DEFAULT '0' COMMENT '0草稿 1已发布',
  `start_time` datetime DEFAULT NULL COMMENT '开始时间',
  `end_time` datetime DEFAULT NULL COMMENT '截止时间',
  `is_deleted` tinyint(1) NOT NULL DEFAULT '0' COMMENT '软删除 0正常 1已删除',
  `gmt_create` datetime DEFAULT CURRENT_TIMESTAMP,
  `gmt_modified` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_creator` (`creator_uid`),
  KEY `idx_status_end` (`status`, `end_time`),
  CONSTRAINT `assignment_ibfk_1` FOREIGN KEY (`creator_uid`) REFERENCES `user_info` (`uuid`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='作业';
```

> `status` 只有 0(草稿)/1(已发布) 两态落库。「未开始/进行中/已结束」由 `start_time`/`end_time` 动态推导，避免定时任务翻转状态（对比比赛 `contest` 有显式 status + 定时任务，作业从简）。

### 3.2 `assignment_problem` 作业题目

```sql
CREATE TABLE IF NOT EXISTS `assignment_problem` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT,
  `aid` bigint(20) unsigned NOT NULL COMMENT '作业id',
  `pid` bigint(20) unsigned NOT NULL COMMENT '题目id',
  `display_id` varchar(20) NOT NULL COMMENT '作业内展示编号 A/B/C',
  `score` int(11) NOT NULL DEFAULT '0' COMMENT '分值(预留,AC制暂用)',
  `sort` int(11) NOT NULL DEFAULT '0' COMMENT '排序',
  `gmt_create` datetime DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_aid_pid` (`aid`, `pid`),
  KEY `idx_pid` (`pid`),
  CONSTRAINT `assignment_problem_ibfk_1` FOREIGN KEY (`aid`) REFERENCES `assignment` (`id`) ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT `assignment_problem_ibfk_2` FOREIGN KEY (`pid`) REFERENCES `problem` (`id`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='作业题目';
```

### 3.3 `student_group` 学生组 + `student_group_user` 成员

```sql
CREATE TABLE IF NOT EXISTS `student_group` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT,
  `name` varchar(100) NOT NULL COMMENT '组名',
  `owner_uid` varchar(32) NOT NULL COMMENT '组主uid',
  `description` varchar(500) DEFAULT NULL COMMENT '组描述',
  `is_deleted` tinyint(1) NOT NULL DEFAULT '0',
  `gmt_create` datetime DEFAULT CURRENT_TIMESTAMP,
  `gmt_modified` datetime DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_owner` (`owner_uid`),
  CONSTRAINT `student_group_ibfk_1` FOREIGN KEY (`owner_uid`) REFERENCES `user_info` (`uuid`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='学生组';

CREATE TABLE IF NOT EXISTS `student_group_user` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT,
  `gid` bigint(20) unsigned NOT NULL COMMENT '学生组id',
  `uid` varchar(32) NOT NULL COMMENT '学生uid',
  `gmt_create` datetime DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_gid_uid` (`gid`, `uid`),
  KEY `idx_uid` (`uid`),
  CONSTRAINT `student_group_user_ibfk_1` FOREIGN KEY (`gid`) REFERENCES `student_group` (`id`) ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT `student_group_user_ibfk_2` FOREIGN KEY (`uid`) REFERENCES `user_info` (`uuid`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='学生组成员';
```

> 为何不复用「团队」`group`/`group_member`：团队带申请/审核/五级权限/头像/邀请码/站内子功能（公告、比赛、训练、讨论、榜单）等重功能，作业只需「命名成员列表」，复用会拖入大量无关复杂度。故独立建表。

### 3.4 `assignment_student` 下发快照 + 完成情况

```sql
CREATE TABLE IF NOT EXISTS `assignment_student` (
  `id` bigint(20) unsigned NOT NULL AUTO_INCREMENT,
  `aid` bigint(20) unsigned NOT NULL COMMENT '作业id',
  `uid` varchar(32) NOT NULL COMMENT '学生uid',
  `is_required` tinyint(1) NOT NULL DEFAULT '0' COMMENT '冗余:是否必做,便于查"必做未完成"',
  `status` tinyint(4) NOT NULL DEFAULT '0' COMMENT '0未完成 1已完成',
  `accepted_count` int(11) NOT NULL DEFAULT '0' COMMENT '已AC题数',
  `score` int(11) NOT NULL DEFAULT '0' COMMENT '得分(预留)',
  `gmt_create` datetime DEFAULT CURRENT_TIMESTAMP COMMENT '下发时间',
  `gmt_finish` datetime DEFAULT NULL COMMENT '完成时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_aid_uid` (`aid`, `uid`),
  KEY `idx_uid_status` (`uid`, `status`),
  KEY `idx_aid_status` (`aid`, `status`),
  CONSTRAINT `assignment_student_ibfk_1` FOREIGN KEY (`aid`) REFERENCES `assignment` (`id`) ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT `assignment_student_ibfk_2` FOREIGN KEY (`uid`) REFERENCES `user_info` (`uuid`) ON DELETE CASCADE ON UPDATE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8 COMMENT='作业下发快照与完成情况';
```

**关键语义**：`assignment_student` 是「下发时快照」。管理员发布作业时，把所选学生组成员展开写入此表；之后改组**不回写**历史作业名单。`accepted_count`/`status` 由评测回调实时维护（见 §6）。

### 3.6 `judge` 加 `aid` 列（幂等）

```sql
DROP PROCEDURE IF EXISTS `add_judge_aid`;
DELIMITER $$
CREATE PROCEDURE `add_judge_aid`()
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM information_schema.COLUMNS
    WHERE table_schema = 'hoj' AND table_name = 'judge' AND column_name = 'aid'
  ) THEN
    ALTER TABLE `judge` ADD COLUMN `aid` bigint(20) unsigned DEFAULT '0' COMMENT '作业id,非作业提交默认为0';
  END IF;
END$$
DELIMITER ;
CALL `add_judge_aid`();
DROP PROCEDURE `add_judge_aid`;
```

> 与 `cid`/`gid` 同语义：`aid=0` 表示非作业提交。好处：作业详情页「每题状态」与「完成重算」都能直接 `SELECT ... FROM judge WHERE aid=? AND uid=?`，无需额外提交关联表。

## 6. 提交与评测回调链路（核心，已对照真实代码定位）

现有链路（已确认源码）：

1. **提交入口** `JudgeManager.submitProblemJudge(SubmitJudgeDTO)`（`manager/oj/JudgeManager.java:108`）：按 `cid!=0` / `tid!=0` / 否则 分派。
2. **初始化** `BeforeDispatchInitManager`（`manager/oj/BeforeDispatchInitManager.java`）：`initCommonSubmission` / `initContestSubmission` / `initTrainingSubmission` —— 各自校验权限、`judgeEntityService.save(judge)`、写关联记录（如 `training_record`）。
3. **评测落库回调** JudgeServer 的 `JudgeServiceImpl.judge()` → `judgeEntityService.updateById(finalJudgeRes)` 后调用 `judgeContext.updateOtherTable(submitId, status, cid, uid, pid, gid, score, useTime)`（`JudgeServer/src/main/java/top/hcode/hoj/judge/JudgeContext.java`）—— 这是 AC 副作用唯一落点：非比赛 AC 写 `user_acproblem`，比赛写 `contest_record`。

作业改动（三处，均为既有模式的延伸）：

1. **`SubmitJudgeDTO` 加 `aid` 字段**（`api` 模块 `pojo/dto/SubmitJudgeDTO.java`），`Judge` 实体加 `aid` 字段（`pojo/entity/judge/Judge.java`，`aid=0` 默认）。
2. **`JudgeManager.submitProblemJudge` 加分支**：
   ```
   boolean isAssignmentSubmission = judgeDto.getAid() != null && judgeDto.getAid() != 0;
   ...
   if (isAssignmentSubmission) {
       beforeDispatchInitManager.initAssignmentSubmission(judgeDto.getAid(), judgeDto.getPid(), userRolesVo, judge);
   } else if (isContestSubmission) { ... } // 顺序: 作业 > 比赛 > 训练 > 普通
   ```
3. **`BeforeDispatchInitManager.initAssignmentSubmission(aid, displayId, userRolesVo, judge)`**：
   - 校验作业存在、已发布、当前用户已被下发（`assignment_student` 有记录）、时间窗内（未开始/已结束抛 `StatusForbiddenException`，仿 `initContestSubmission` 的 status 校验）。
   - 解析 `displayId → pid`（查 `assignment_problem`），设置 `judge.setAid(aid).setPid(pid).setDisplayPid(problem.getProblemId())`，`judgeEntityService.save(judge)`。
   - 不额外写提交关联表（`aid` 列已足够定位）。

4. **完成判定（评测落库）** —— `JudgeContext.updateOtherTable` 增加参数 `aid` 与分支：
   ```
   if (aid != 0 && status == STATUS_ACCEPTED) {
       // 重算该学生在此作业的完成情况: 影响范围 = 单个 (aid, uid)
       int acCount = countDistinctPidWhereAidAndUidAndAccepted(aid, uid);
       int total = countAssignmentProblem(aid);
       assignmentStudentService.saveOrUpdate(  // upsert
           new AssignmentStudent().setAid(aid).setUid(uid)
             .setAcceptedCount(acCount)
             .setStatus(acCount >= total ? 1 : 0)
             .setGmtFinish(acCount >= total ? new Date() : null)
       );
   }
   ```
   - JudgeServer 侧需新增自己的 `dao`（`AssignmentStudentEntityService` + mapper），与其已有的 `UserAcproblemEntityService`/`ContestRecordEntityService` 同理（JudgeServer 与 DataBackup 共享同一 MySQL，各自持有需要的 dao）。
   - 单次 AC 只影响一个 `(aid, uid)` 快照行，开销可忽略；给 navbar「未完成数」和管理统计提供 O(1) 查询。

**注意事项**：
- `updateOtherTable` 签名需从 `(submitId,status,cid,uid,pid,gid,score,useTime)` 扩展为 `(submitId,status,cid,aid,uid,pid,gid,score,useTime)`，由 `JudgeServiceImpl.judge()` 传 `judge.getAid()`。
- **重判（Rejudge）**：`manager/admin/rejudge/RejudgeManager` 重判后也应触发同款重算（补一条回调），避免重判改变 AC 后快照失真 —— 记入实现清单。
- 提交频率限制：作业提交非比赛提交，命中 `defaultSubmitInterval` 限流（`JudgeManager` 现有逻辑，无需改动，仅确认语义可接受）。

## 9. 边界与风险

- **重判一致性**：重判改变 AC 结果后必须同步重算快照，否则 `accepted_count` 失真（已列入 §8.2）。
- **快照不回写**：发布后改组/改人，不影响已下发名单（`assignment_student` 是历史快照）；编辑作业发布后题目集锁定（只可改标题/说明/延期），避免与已交进度对不上。
- **时间窗推导**：`status` 只落库 0/1，前端/接口动态算「进行中/已结束」，不引入定时任务（相对比赛的刻意简化）。
- **范围隔离默认开启**：普通 admin 只能看/管自己的作业与组；root 全局；`problem_admin` 只读。
- **微信家长**：本轮仅建表 + 预留接口，小程序前端与绑定码安全（一次性、限尝试次数、学号+姓名二次校验）单独排期。
