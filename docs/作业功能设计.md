# 「作业」功能设计

> 状态：设计稿（待拍板后进入实现）
> 关联改动：`/assignment` 路由 + 占位页 + navbar「作业」入口已就位；原「团队」功能归档，入口移入「更多 → 团队(弃用)」。

## 1. 角色与权限（先回答「合不合理」）

**结论：三个角色都做满 CRUD 不太合理，建议收敛。** 矛盾点在「题目管理员」和「删除」。

角色对应（`sqlAndsetting/hoj.sql` 的 `role` 表）：`root`=超级管理员、`admin`=普通管理员、`problem_admin`=题目管理员。

| 操作 | root | admin | problem_admin | 学生 |
|---|---|---|---|---|
| 新建作业 | ✅ | ✅（仅自己的） | ⚠️ 建议不给/仅草稿 | — |
| 编辑作业 | ✅ 全部 | ✅ 仅自己的、发布前可改题目 | ⚠️ 建议不给 | — |
| 查询作业（管理视图） | ✅ 全局 | ✅ 仅自己的 | 🔸 只读 | 🔸 只读「布置给我的」 |
| 删除作业 | ✅ 全部 | ✅ 仅自己的 | ❌ 建议不给 | — |

理由：

1. **题目管理员的职责是「题目」，不是「教务」。** 作业 = 选题 + 下发学生 + 跟踪成绩，后两件与题目管理无关。小团队若角色混用，放开「查询 + 建草稿」足够。
2. **删除是破坏性操作，必须收紧：** 建议软删除，默认「只能删自己创建的作业」，root 才可删任意；已有人提交的作业删除需二次确认。
3. **编辑要分阶段锁：** 作业「发布」后题目集不可改（否则与已交进度对不上），只能改标题/说明/延长截止时间。
4. **范围隔离（建议默认开启）：** 普通管理员只看/管自己创建的作业和学生组，root 全局可见。

## 2. 核心概念与「完成」定义

- **作业（Assignment）** = 一组题目 + 下发对象（学生）+ 时间窗口 + 是否必做。
- **必做（required）** = 截止前必须完成，未完成触发 navbar 闪烁和微信端提醒。
- **「完成」定义（待拍板，推荐 A）：**
  - A. AC 制：作业内所有题都被该学生 AC → 完成。
  - B. 提交制：所有题都提交过 → 完成。
  - C. 分数制：总分达到阈值 → 完成。

## 3. 数据模型（新增表）

```
assignment                   作业
  id             bigint PK
  title          varchar(200)
  description    mediumtext
  creator_uid    varchar(32)  创建者(管理员)
  is_required    tinyint      1必做 0选做
  status         tinyint      0草稿 1已发布 2已结束
  start_time     datetime
  end_time       datetime
  is_deleted     tinyint      软删除
  gmt_create / gmt_modified

assignment_problem          作业题目
  id / assignment_id / problem_id / display_id(A/B/C) / score / sort

student_group               学生组
  id / name / owner_uid / description / is_deleted / gmt_create / gmt_modified

student_group_user          学生组成员
  id / group_id / uid / gmt_create   UNIQUE(group_id, uid)

assignment_student          下发对象 + 完成情况【快照】
  id / assignment_id / uid
  is_required tinyint        冗余，方便查"必做未完成"
  status tinyint             0未完成 1已完成
  accepted_count int         已AC题数
  score int                  得分(可选)
  gmt_create(下发时间) / gmt_finish(完成时间)
  UNIQUE(assignment_id, uid)

parent_binding              家长-孩子绑定
  id / parent_openid / student_uid / bind_code / status(0待确认 1已绑定 2已解绑) / gmt

wechat_user                 微信身份映射
  openid varchar(64) PK / uid(平台账号,可空) / nickname / avatar / gmt_create
```

**关键：`assignment_student` 是「下发时快照」。** 下发时把所选学生组成员展开写入此表，之后改组不回头改历史作业名单。

## 4. 学生组

- 管理员维护自己的学生组（CRUD 成员）。
- 下发作业时选组（可多选），也能临时手动加人；后端在下发那一刻快照进 `assignment_student`。
- 组按 `owner_uid` 隔离，root 可管所有组。

## 5. 后端接口（REST，`/api/assignment/*`）

```
管理员侧
POST   /assignment                  新建(草稿/发布)
PUT    /assignment/{id}             编辑(发布前可改题目/发布后只可延期)
DELETE /assignment/{id}             删除(软删除, 限创建者/root)
GET    /assignment/list             管理查询(自己的, 含草稿, 分页)
GET    /assignment/{id}             详情(含题目+下发人数+完成统计)
POST   /assignment/{id}/publish     发布
POST   /assignment/{id}/extend      延长截止时间

学生组
POST/PUT/DELETE /assignment/group           组CRUD
POST/DELETE /assignment/group/{gid}/user    加/删成员

学生侧
GET    /assignment/my                布置给我的作业(未完成在前)
GET    /assignment/my/{id}           单份作业+我的完成进度

通知
GET    /assignment/unfinished-count  必做未完成数量(navbar闪烁用)

微信小程序侧(预留)
POST   /wechat/login                 code -> openid -> token
POST   /wechat/bind                  绑定孩子(绑定码 + 学号/姓名二次校验)
GET    /wechat/child/list            已绑定孩子
GET    /wechat/child/{uid}/assignments           孩子作业列表
GET    /wechat/child/{uid}/assignment/{aid}       单份作业实时完成情况
```

「实时完成」：评测回调（judge 落库时）同步刷新 `assignment_student.accepted_count/status`，小程序轮询 realtime 接口（10~30s），后续可上 WebSocket。

## 6. 前端（navbar 闪烁 + 页面）

**闪烁**（复用 NavBar 现有 PK 轮询）：
1. 登录后 + 定时器(60s) 调 `GET /assignment/unfinished-count`。
2. `n > 0` 给「作业」菜单项加闪烁 class（CSS keyframes），`n == 0` 移除。
3. 完成最后一份必做后，下次轮询自动停闪；点进作业页时重查一次。

**页面**（替换占位 `AssignmentList.vue`）：
- 学生视图 `/assignment`：布置给我的作业，未完成标红置顶，必做未完成带角标。
- 管理员视图 `/assignment/manage`：列表 + 新建/编辑/下发向导（选题 → 选学生组 → 设时间/必做）。

## 7. 微信小程序 + 家长绑定

- **绑定流程（安全）**：学生端生成一次性、短时效绑定码（或二维码带 token）→ 家长扫码进小程序 → 输入孩子「学号 + 真实姓名」二次校验 → 写入 `parent_binding`。绑定码一次性、限尝试次数。
- **家长视图**：孩子作业列表 + 单份作业实时完成情况（每题 AC/未做/得分），必做未完成标红。
- **权限**：家长只能看自己绑定的孩子，接口按 `openid` 强制过滤。
- **范围**：本轮先留接口 + 数据模型，小程序前端单独排期。
