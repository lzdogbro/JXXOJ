## 2. 数据库迁移（增量，幂等）

```sql
USE `hoj`;

-- 1) parent_openid 允许 NULL（生成绑定码时还没有家长 openid）
ALTER TABLE `parent_binding`
  MODIFY COLUMN `parent_openid` varchar(64) DEFAULT NULL COMMENT '家长openid,生成码阶段为NULL';

-- 2) 补绑定码生命周期两列
ALTER TABLE `parent_binding`
  ADD COLUMN `gmt_expire` datetime DEFAULT NULL COMMENT '绑定码过期时间' AFTER `status`,
  ADD COLUMN `attempt_count` int(11) NOT NULL DEFAULT '0' COMMENT '校验失败次数' AFTER `gmt_expire`;

-- 3) 可选：同一家长对同一孩子仅一条有效绑定，防重复

```

> `status` 语义扩展：0 待确认 / 1 已绑定 / 2 已解绑 / 3 已失效（过期或烧毁）。

## 4. 认证体系（核心改动）

### 4.1 Redis 前缀

`ShiroConstant.java` 追加：

```java
public final static String WECHAT_TOKEN_KEY = "shiro:token-key:wechat:";
```

### 4.2 token 签发/校验

`JwtUtils.java` 追加微信侧方法（复用同一 secret，`getClaimByToken` 已共享）：

```java
public String generateWechatToken(String openid) {
    // 同 generateToken，但 Redis key 用 WECHAT_TOKEN_KEY，不写 refresh key（小程序会话无需刷新）
}
public boolean hasWechatToken(String openid) {
    return redisUtils.hasKey(ShiroConstant.WECHAT_TOKEN_KEY + openid);
}
public void cleanWechatToken(String openid) { ... }
```

### 4.3 微信 principal

新增 `shiro/WechatProfile.java`：仅 `openid`（`getId()` 返回 openid，对齐 `AccountProfile` 的约定）。

### 4.4 `WechatRealm`

新增 `shiro/WechatRealm.java`，仿 `AccountRealm`：
- `supports` 判断 token 类型（可复用 `JwtToken`，或新 `WechatToken`；建议直接复用 `JwtToken`）。
- `doGetAuthenticationInfo`：`getClaimByToken(subject=openid)` → `wechat_user` 按 openid 查（存在且未封禁）→ 返回 `SimpleAuthenticationInfo(new WechatProfile(openid), ...)`。
- **不查** `user_info`（家长无平台账号，`wechat_user.uid` 恒 NULL）。
- 授权信息：家长无角色/权限，`doGetAuthorizationInfo` 返回空 `SimpleAuthorizationInfo`（不继承平台角色）。

### 4.5 `WechatJwtFilter`

新增 `shiro/WechatJwtFilter.java`，仿 `JwtFilter`，差异点：
1. **剥离 `Bearer ` 前缀**：`Authorization` 头形如 `Bearer <token>`（平台前端是裸 token，平台 filter 不动，只在微信 filter 里剥）。
2. 校验用 `hasWechatToken(openid)`（前缀 `wechat:`）。
3. `@AnonApi` 处理逻辑照抄（`/api/wechat/login` 需匿名）。
4. 不实现 token 刷新（可选省略 `refreshToken`）。

### 4.6 Shiro 链（`ShiroConfig.shiroFilterChainDefinition`）

Shiro 链是 **首个匹配生效**，更具体的路径放前面：

```java
filterMap.put("/api/wechat/bind-code", "jwt");   // 平台登录态（学生本人）
filterMap.put("/api/wechat/login", "anon");       // 或保留 jwt + @AnonApi，二选一
filterMap.put("/api/wechat/**", "wechatJwt");     // 微信登录态
filterMap.put("/**", "jwt");                      // 平台（原有）
```

`shiroFilterFactoryBean` 里注册 `filters.put("wechatJwt", wechatJwtFilter);`。

> 关键点：`/api/wechat/bind-code` 虽挂在 `/api/wechat/**` 下，但必须走平台 `jwt`，所以显式列在 `/api/wechat/**` 之前。

## 7. 各接口实现要点

### 7.1 login（`/api/wechat/login`）
1. 入参 `code` 非空校验。
2. `HttpUtil.get("https://api.weixin.qq.com/sns/jscode2session?appid=...&secret=...&js_code=...&grant_type=authorization_code")`，解析 `{openid, session_key}`；失败（无 openid）→ 500。
3. `wechat_user` upsert（openid 存在则更新 nickname/avatar，不存在则插入，`uid` 置 NULL）。
4. `jwtUtils.generateWechatToken(openid)` → `WechatLoginVO{token, openid, hasChild}`。
5. `hasChild` = 是否存在 `parent_binding(parent_openid=openid, status=1)`。

### 7.2 bind-code（平台登录态）
1. `AccountProfile` 取当前学生 uid。
2. 生成 6 位码（去 0/O、1/I/l，大写字母+数字）。
3. `parent_binding` 插入 `parent_openid=NULL, student_uid=uid, bind_code, status=0, gmt_expire=now+600s, attempt_count=0`。
4. 返回 `{bindCode, expireIn:600}`。旧码不主动作废，自然过期。

### 7.3 bind（微信登录态，核心）
1. 按 `bind_code` 查 `parent_binding`：
   - 不存在 → 400「绑定码无效」；
   - `status != 0` → 400「绑定码已使用」；
   - `gmt_expire < now` → 置 `status=3` → 400「绑定码已过期，请重新生成」。
2. `attempt_count += 1`（`updateById` 原子累加）；`> 5` → 置 `status=3` → 400「尝试次数超限，请重新生成」。
3. 二次校验：用 `student_uid` 查 `user_info`，比对 `number`（去空格）与 `realname`（规范化大小写/空格）→ 不匹配 400「学号或姓名不匹配」，保留 attempt_count。
4. 匹配 → `parent_openid=当前openid, status=1, gmt_modified=now`，返回 `ChildVO`。

> 注意 `bind_code` 唯一键已存在，第 1 步单行 `getOne` 即可。并发下建议在 `attempt_count` 累加处用 `UpdateWrapper` 条件更新，避免超卖（可后置优化）。

### 7.4 unbind / child/list
- `unbind`：按 `(parent_openid, student_uid)` 查 `status=1` 的记录，无 → 404；置 `status=2`。仅本人（openid 匹配）→ 天然满足。
- `child/list`：`parent_binding(parent_openid=openid, status=1)` → 逐个 join `user_info` 组装 `ChildVO`（含 `boundAt=gmt_modified`）。

### 7.5 child assignments（列表，**最大复用**）
1. 越权校验：`parent_binding(parent_openid=openid, student_uid=uid, status=1)` 不存在 → 403。
2. 直接调用 `assignmentEntityService.getMyAssignmentList(page, uid)` —— 该 SQL 已按 `s.uid=#{uid}` 过滤，**孩子视角与「我的作业」同一条 SQL**。
3. 对每条 record 调 `computeTimeStatus(vo)` + `setCompleted(isCompleted(vo))`（这两个私有方法需在 `AssignmentManager` 提为 public，或复制 3 行逻辑到 `WechatAssignmentManager`）。

### 7.6 child assignment detail（详情，需新 SQL）
1. 越权校验同上 + `checkAssigned(aid, uid)`（该作业确已下发给孩子）。
2. 基础字段复用 `checkAndGetAssignment` + `computeTimeStatus`。
3. 题目列表 + 3 态状态：**新增一条 SQL**（见下），返回每题「是否 AC / 是否提交过 / 最新提交时间」：
   - `AC`：该 pid 存在 `status=ACCEPTED` 的 judge；
   - `已提交未AC`：有 judge 记录但无 AC；
   - `未做`：无 judge 记录。
4. `acceptedCount` 由 AC 题数统计，`completed = acceptedCount >= problemCount`。

新增 mapper（`AssignmentProblemMapper` 或 `JudgeMapper`）方法示意：
```

-- SELECT ap.pid, ap.display_id, p.title, ap.score,
```

> 平台学生视图当前只用「AC/未AC」两态（`getAcceptedPidsByAidUid`），家长侧要 3 态，故需新查询，不能完全复用。

### 7.7 subscribe（订阅授权上报）
1. 校验 `eventType ∈ {assignment_publish, assignment_done}`，否则 400。
2. `redisUtils.incr("wechat:sub:" + openid + ":" + templateId, 1)`。
3. 返回 `data=null`。

## 8. 通知推送（订阅消息）

### 8.1 发送器（新 `service/wechat/WechatMessageService`）
- 入口 `sendSubscribeMessage(openid, templateId, Map<String,Object> data, eventType)`：
  1. 先 `decr` 配额，`<= 0` 则不再推（原子 `decr` 后判断，避免多线程超发）；
  2. 拿 `access_token`（`getAccessToken`，缓存到 Redis，`expire` 提前 60s）；
  3. `HttpUtil.post("https://api.weixin.qq.com/cgi-bin/message/subscribe/send?access_token=...")` 发订阅消息；
  4. 失败静默重试 1 次，不抛业务异常。

### 8.2 触发点①：作业发布
`AdminAssignmentManager.publishAssignment()`（及 `addAssignment` 直接发布分支）在 `publishMembers` 写快照后：
1. 收集本次下发的 `uidSet`；
2. 异步（`@Async` 或线程池）查每个 uid 的 `parent_binding(status=1)` 家长 openid 列表；
3. 逐个查订阅配额 → 发「新作业」（孩子姓名 + 作业标题 + 截止时间）。

> 放在 `publishMembers` 之后、`updateById(status=1)` 之前或之后均可，但必须在事务提交后异步发（避免事务回滚还发了通知）。

### 8.3 触发点②：作业完成
`updateCompletion`（`DataBackup` 与 `JudgeServer` 两个模块各一份，逻辑一致）在更新前已读到 `existing.getStatus()`：
```java
boolean justCompleted = existing != null && existing.getStatus() == 0 && completed;
// ... update ...
if (justCompleted) {
    wechatMessageService.notifyAssignmentDone(aid, uid); // 异步
}
```
- **两处都加**：判题侧（`JudgeServer`）正常提交、重判侧（`DataBackup/RejudgeManager`）都会触发。
- **防重判重复推送**：只有 `status 0→1` 翻转点才发；重判后若 `accepted_count` 回落（completed=false）再完成，`status` 已从 1 回 0，会再次翻转——符合「再次完成再通知」的预期，属可接受；若要严格只发一次，需加 `notified` 位（二期）。

> JudgeServer 也要能拿到 wechat 配置（appid/secret/模板 id），故 `hoj.wechat` 配置需在 JudgeServer 的 `application.yml` 同步（或通过 Nacos 下发）。若嫌 JudgeServer 引入发送逻辑重，也可只在 `DataBackup` 侧做：重判链路本就在 DataBackup，正常判题完成后 JudgeServer 通过现有回调/消息通知 DataBackup——但当前架构无该通道，**建议直接在两处内联发送**。

## 9. 关键坑（实现前必须处理）

1. **`parent_binding.parent_openid` 现为 `NOT NULL`**：§2 迁移必须先跑，否则「生成绑定码」插 NULL 直接报错。
2. **`Bearer ` 前缀**：微信侧 `Authorization: Bearer <token>`，`WechatJwtFilter.createToken` 要剥 `Bearer `；平台 `JwtFilter` 别动（平台是裸 token）。
3. **`/api/wechat/bind-code` 走平台 JWT**：Shiro 链顺序要把它列在 `/api/wechat/**` 之前映射到 `jwt`。
4. **作业详情 3 态 ≠ 平台 2 态**：家长侧要「AC / 已提交未AC / 未做」+ submitTime，需新 SQL，不能只复用 `getAcceptedPidsByAidUid`。
5. **`updateCompletion` 有两份**：`JudgeServer` 与 `DataBackup` 各一份，完成通知两处都要埋点，否则重判完成的作业不会推。
6. **两个实体在 `api` 共享模块**：改 `ParentBinding` 会同时重编译 JudgeServer，确认 JudgeServer 也能解析新字段（无副作用，只是多两列映射）。
7. **`ChildVO.school`**：`user_info.school` 已存在，直接映射即可，无需迁移。

## 10. 分阶段实施顺序

| 阶段 | 内容 | 验收 |
|---|---|---|
| A | §2 迁移 + §3 实体 + §4 认证（Realm/Filter/Shiro 链）+ §5 配置 | `curl /api/wechat/login` 能换 openid 签 token |
| B | 登录 + bind-code + bind/unbind + child/list | 家长能绑定孩子、看到孩子列表 |
